# AI 품질처리 MLOps 운영기준 결정안

작성일: 2026-09-23  
상태: 기술 기준 확정안, 운영 승인 대기

## 2026-10-06 적용 범위 정정

사용자 결정에 따라 기존 AI 소스는 변경하지 않는다. `N1_AQC_FLAG`의 AI 위치는 기존 11번째 자리 그대로 보존하며 운영 DB 연결과 출력 구조 재설계는 현재 작업에서 제외한다. 운영 서버 반입본의 실행 경로, 입력, 모델, 로컬 결과와 상태 저장을 문서로 정리한다. 이 문서의 설정 분리, 새 파이프라인, 승인·배포·되돌리기 내용은 향후 설계안으로만 보관하며 기존 소스를 수정하는 근거로 사용하지 않는다. 운영 프로세스가 활성 manifest를 읽도록 바꾸는 작업도 현재 수행하지 않는다.

반입 자료의 검토 결과와 파일 목록은 `reports/20261006_operational_import/summary.json`, `reports/20261006_operational_import/file_inventory.csv`에 있다. 기존 문서는 같은 보고서 폴더의 `documentation_before`에 보존했다.

## 적용 원칙

2025년 운영본은 비교 기준선으로 보존하고 직접 리팩토링하지 않는다. 2026년 후보 파이프라인은 별도 저장소와 실행 경로에서 만든다. 자동화는 학습과 시험까지 허용하되 운영 승격은 담당자 승인 전에는 실행하지 않는다.

## 1. 데이터 버전과 학습 대상 기간

데이터 버전은 파일명이나 폴더 날짜가 아니라 `dataset_id`와 SHA-256으로 고정한다. DB에서 추출할 때는 조회 시작·종료 시각, 관측소, 센서, 조회 조건, 행 수, 최소·최대 관측시각, 결측률, 추출 SQL 버전도 함께 기록한다.

학습 대상은 관측자료와 예측자료가 같은 시각으로 결합된 구간이며, 기존 학습과 같이 정상 품질값만 사용한다. 관측소·센서별 유효자료가 최소 365일 이상일 때만 학습 대상으로 인정한다. 기간은 미래 자료가 검증 구간에 섞이지 않도록 시간 순서대로 학습 80%, 검증 20%로 나눈다. 이 기준은 2026년 신규 학습부터 적용하고 2025년 기준선에 소급 적용하지 않는다.

## 2. 실행별 매개변수·성능·산출물 추적

실행 추적 도구는 사내망에 설치한 MLflow 2.x를 우선안으로 정한다. 기존 소스는 당장 MLflow 코드를 넣지 않고 외부 wrapper가 한 번의 학습을 하나의 run으로 등록한다. MLflow 공식 기능에 맞춰 매개변수, 성능지표, 태그, 입력 데이터 식별자와 산출물을 기록한다.

필수 매개변수는 입력 길이, epoch 상한, batch 크기, optimizer, loss, LSTM unit, 조기 종료 patience, 학습·검증 비율, 난수 seed, TensorFlow와 Python 버전이다. 필수 성능은 검증 MAE, RMSE, 평균 절대오차, 오차 표준편차, 계산된 임계값, 검증 표본 수다. 필수 산출물은 모델, scaler, 임계값, 검증 예측 CSV, loss 그래프, 실행 로그, 데이터 manifest, 소스 commit 또는 소스 묶음 해시다.

2025년 소스는 일부 값을 로그와 파일에 남기지만 하나의 실행 ID로 묶지 않는다. 따라서 과거 결과는 `IMPORTED_LEGACY`로 등록하고, 재현 가능하다고 표시하지 않는다.

## 3. 모델 등록, 승인, 운영 승격과 되돌리기

등록 단위는 `관측소 코드 + 센서 코드` 한 조합이다. 한 등록 모델 아래에 학습 실행별 버전을 만든다. MLflow의 단계(stage)는 폐지 예정이므로 사용하지 않고 `candidate`, `champion`, `rollback` alias와 버전 태그를 사용한다.

후보 등록은 자동화할 수 있다. `candidate` 지정은 필수 파일, 해시, 모델 로딩, 재현 시험, 성능 기준을 모두 통과해야 한다. `champion` 변경은 AI 담당자와 운영 담당자의 승인을 모두 기록한 뒤에만 수행한다. 승격 직전 champion은 `rollback`으로 유지한다. 되돌리기는 이전 manifest를 다시 활성화하는 방식으로 하며 모델 파일을 덮어쓰지 않는다.

## 4. 정기 또는 조건 기반 재학습

매월 첫 영업일에 재학습 필요 여부를 자동 점검한다. 정기 재학습은 연 1회 실시하되, 최근 365일 이상의 유효자료가 있는 조합만 대상으로 한다. 아래 조건 중 하나가 7일 연속 이어지면 조건 기반 재학습 후보를 만든다.

- 최근 30일 MAE가 승인 기준선보다 20% 이상 증가
- 입력 결측률이 기준선의 2배 이상
- 예측 오차 분포의 중앙값 또는 상위 95% 값이 기준선 허용 범위를 벗어남
- 센서 교체, 관측소 이전, 예측자료 생산 방식 변경

조건을 만족해도 자동으로 운영에 올리지 않는다. 자동화 범위는 데이터 추출, 학습, 평가, 후보 등록까지이며 운영 승격은 승인 절차를 따른다.

## 5. 시험 통과 후 해역별 배포 자동화

동해·서해·남해별 release manifest를 만든다. 배포 단위는 모델 하나가 아니라 해당 해역의 소스, 매핑, 모델, scaler, 임계값, 환경을 묶은 불변 release다.

배포 전에는 스키마 검사, 해시 확인, 64개 전체 모델 로딩, 고정 입력 예측, 과거자료 재생, DB 쓰기 없는 shadow 실행을 차례로 통과해야 한다. shadow 기간은 최소 7일로 정한다. 배포는 새 release 폴더를 만든 뒤 활성 manifest 포인터만 원자적으로 바꾼다. 실패하면 이전 manifest 포인터로 되돌린다.

현재 소스의 DB 갱신 경로는 별도 승인 전까지 자동 배포 시험에서 제외한다. `no_update` 실행과 재생 시험으로 먼저 결과 일치 여부를 확인한다.

## 6. 운영 감시

감시는 모델 성능뿐 아니라 입력과 실행 상태를 함께 본다. 1분 자료를 기준으로 초기 경보 기준을 다음과 같이 정하고, 4주간 병행운영 자료로 조정한다.

- 입력 지연: 마지막 관측시각이 현재보다 5분 이상 늦으면 경고, 10분 이상이면 장애
- 연속 결측: 5개 이상 경고, 10개 이상 장애
- 예측 오차: 7일 이동 MAE가 champion 검증 MAE보다 20% 이상 증가하면 재학습 검토
- 플래그 분포: 조합별 비정상 플래그 비율이 최근 30일 중앙값의 2배를 넘으면 경고
- 모델 저하: 30일 MAE 또는 오차 상위 95% 값이 승인 기준을 7일 연속 넘으면 후보 재학습
- 실행 상태: 모델 로딩 실패, scaler/임계값 누락, 해시 불일치, 작업 종료코드 비정상은 즉시 장애

관측소 점검이나 통신 장애처럼 모델 문제가 아닌 원인을 구분하기 위해 입력 상태 경보와 모델 성능 경보를 따로 저장한다.

## 7. 단일 버전 manifest

운영 release마다 manifest 하나를 만들고 `release_id`를 변경 불가능한 식별자로 사용한다. manifest에는 데이터, 소스, 환경, 매핑, 64개 모델·scaler·임계값의 경로와 SHA-256, 승인 기록, 배포 대상 해역, 이전 release ID를 기록한다.

비밀번호, DB 접속 문자열, 개인키는 manifest에 넣지 않는다. manifest 자체에도 SHA-256을 계산하고 승인 서명 또는 승인 기록과 함께 보관한다. 운영 프로세스는 개별 파일 경로를 직접 조합하지 않고 활성 manifest만 읽어야 한다.

## 8. 재학습 데이터 준비와 fine-tuning 권한

기본 재학습은 사용자가 선택한 기간의 snapshot으로 모델과 scaler를 처음부터 새로 만든다. fine-tuning은 기준 모델과 scaler, replay 자료, 학습률, epoch, optimizer 상태, 과거 대표기간 회귀시험을 모두 관리해야 하므로 전문가 권한에서만 실행하고 자동 운영 승격을 금지한다.

기간 선택 직후에는 예상 1분 건수를 표시하고, 승인된 비부하 시간대의 DB Export 후에는 관측·예측 유효 결합 건수, 유효율, 건수÷1,440 환산 일수, 실제 연속 구간, 최장 결측과 월별 분포를 표시한다. 환산 일수는 연속된 실제 일수와 구분한다.

학습은 최종 Export 파일만 사용하며 `.part`, 0바이트, 기간 불일치, 중복 충돌 미해결 파일은 차단한다. 관측·예측 결합 후 1분 연속 구간별로 입력창을 만들고, 시간순 분할을 먼저 수행한 뒤 scaler는 학습 구간에만 맞춘다.

## 시행 순서

1. 실제 운영 서버의 소스·매핑·모델·환경 해시를 읽기 전용으로 수집해 로컬 기준선과 대조한다.
2. 2026년 후보 저장소에 외부 실행 wrapper와 manifest 검증기를 만든다.
3. MLflow 시험 서버에서 과거 결과 1개와 신규 시험 실행 1개를 등록한다.
4. 64개 전체 로딩 시험과 과거자료 재생 기준을 확정한다.
5. `no_update` 기반 7일 shadow 실행 후 승인·승격·되돌리기를 모의시험한다.
6. 운영 DB 쓰기는 마지막 단계에서 별도 승인 후 검증한다.

## 승인이 필요한 항목

기술 기준은 위와 같이 정할 수 있지만 실제 운영 전에는 운영 SLA, 경보 수신자, 승인권자, MLflow 서버 위치와 백업 정책, 운영 서버의 배포·되돌리기 권한을 담당자와 정보화팀이 승인해야 한다.
