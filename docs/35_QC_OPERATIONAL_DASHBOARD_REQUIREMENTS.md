# 35. 품질 현황 운영 대시보드 요구사항

요청일: 2026-10-09. 사용자 제공 요구사항을 보존한다. 본문은 구현 완료 보고가 아니라 개발·검증의 수용 기준이다.

제공 텍스트 SHA-256: `e96d3a737224a662fe261e15bdad61ba3d590a92e100d86c9cd51c481c1dc200`. 역할·구현·검증 상태는 [36 실행 기록](36_QC_OPERATIONAL_DASHBOARD_EXECUTION.md)을 따른다.

---

Ocean-AI 저장소의 현재 “품질 현황(QC)” 화면을 분석한 뒤, 아래 요구사항에 맞게 실제 코드까지 수정·개발해줘.

중요:
- 먼저 현재 프런트엔드/백엔드 구조, QC 관련 API, DB 모델, Flag 체계, 현재 화면 구현을 실제 코드에서 확인한다.
- 현재 존재하는 QC Flag 코드와 의미를 임의로 바꾸지 않는다. 코드북/백엔드 정의를 먼저 확인한 뒤 UI 라벨을 연결한다.
- 현재 화면 디자인 톤, 좌측 메뉴, 카드 스타일, 차트 스타일은 최대한 유지한다.
- 정적 숫자나 임의 Mock 데이터를 운영 화면에 넣지 않는다.
- 기존 기능을 깨지 않도록 수정하고, 변경한 파일과 이유를 마지막에 정리한다.

==================================================
1. 품질 현황(QC) 화면의 역할 재정의
==================================================

이 화면은 “장기간 분석 화면”이 아니라,

“오늘 국가해양관측망에서 지속적으로 들어오는 관측자료의 1차 QC 상태를 빠르게 확인하고, 검토가 필요한 이상건을 선별하는 운영 대시보드”

로 정의한다.

국가해양관측망의 조위, 수온, 염분, 기압, 기온, 풍속/풍향 등의 자료는 1분 또는 각 관측항목의 원래 관측주기에 따라 계속 유입된다.

따라서 품질 현황 화면에서는 다음 질문에 바로 답할 수 있어야 한다.

1) 오늘 자료가 정상적으로 들어오고 있는가?
2) 어느 관측소/관측항목에서 문제가 발생했는가?
3) 어떤 Rule QC에서 이상이 탐지되었는가?
4) 지연, 결측, Spike, 고정값 등 어떤 문제가 발생했는가?
5) 지금 담당자가 우선 검토해야 할 이상사례는 무엇인가?

AI가 왜 이상이라고 판단했는지, 정상 예상값이 얼마였는지, Residual이 얼마인지는 “주요 이상 사례 상세검토” 단계에서 보여준다.

==================================================
2. 조회기간 UX 변경
==================================================

현재 장기간 범위가 기본값으로 잡혀 있다면 수정한다.

기본 조회:
- 오늘 00:00 ~ 현재시각
- timezone은 현재 시스템의 운영 기준을 그대로 사용하고 임의로 UTC/KST 변환하지 말 것
- backend에서 사용하는 시간 기준을 확인해서 일관되게 처리

상단 빠른 기간 선택:
- 오늘
- 어제
- 최근 7일
- 최근 30일
- 사용자 지정

단,
“품질 현황” 화면의 기본 상태는 반드시 “오늘”이다.

오늘을 선택했을 때:
- 시간대별(hourly) 품질 변화
- 오늘 발생한 Rule QC
- 오늘 관측소×관측항목 현황
- 오늘 주요 이상사례
가 표시되어야 한다.

최근 7일/30일은 장기 경향을 확인하기 위한 보조 조회다.

==================================================
3. 상단 KPI 카드 수정
==================================================

상단 KPI는 선택된 조회기간 기준으로 계산한다.

표시 항목:
- 정상률
- 주의/Suspect 비율
- BAD 비율
- 결측률
- 승인/검토 대기 건수
- 품질처리 완료 건수

가능하면 비율과 건수를 함께 확인할 수 있도록 한다.

예:
정상률 96.4%
980,452건

중요:
- 분모/분자 계산 기준은 현재 QC Flag 정의와 DB 구조를 확인해서 사용한다.
- 임의로 Flag 의미를 새로 정의하지 않는다.
- 데이터가 없으면 0으로 위장하지 말고 “데이터 없음” 상태를 구분한다.

==================================================
4. “품질 Flag 분포” 수정
==================================================

선택된 기간, 기본적으로 오늘의 QC Flag 분포를 보여준다.

도넛/파이 차트:
- 정상
- 주의/의심
- BAD
- 결측
- 미확인 또는 기타 현재 시스템 Flag

각 항목:
- 비율
- 건수
- 클릭 시 해당 상태 자료 필터링

중요:
IOC 또는 현재 내부 Flag 체계는 실제 backend 정의를 확인한 뒤 사용한다.
UI에 하드코딩하지 않는다.

==================================================
5. “품질상태 변화 추이” 수정
==================================================

현재 24개월 등 장기 그래프라면 품질 현황 목적과 맞지 않는다.

오늘 조회 시:
- X축 = 시간대(00시~현재)
- 각 시간대별 정상/주의/BAD/결측 비율 또는 건수
- 1분 원자료를 그대로 수천 개 Plot하지 말고 시간 단위로 집계

최근 7일 선택:
- 일 단위 집계

최근 30일 선택:
- 일 단위 집계

사용자가 기간을 바꾸면 집계 granularity를 적절하게 변경한다.

별도로 “장기 품질 추이” 화면이 존재한다면 그쪽으로 장기 분석을 분리해도 된다.

==================================================
6. “규칙 기반 QC 결과” 수정
==================================================

이 영역은 1차 Rule QC가 오늘 무엇을 탐지했는지 보여주는 영역이다.

예:
- 시간 오류
- 지연 수신
- 결측
- 오류값
- 물리적 범위 초과
- Spike/튐값
- 고정값
- 변화율
- 내부 일관성
- 센서/장비 관련 Rule
- 기타 현재 코드에 구현된 QC Rule

표시:
- 탐지 유형
- 탐지 건수
- 전체 이상 중 비율

Rule 이름은 현재 실제 QC Rule Definition을 기준으로 동적으로 표시하도록 한다.

중요:
1차 QC 단계에서 예측값으로 데이터를 대체하거나 결측을 보간하지 않는다.

예:
10:00 정상
10:01 정상
10:02 자료 미수신
10:03 정상

1차 QC에서는:
10:02 = 결측/지연 관련 Flag

로 표시한다.

“10:02의 예상값은 125cm였을 것이다” 같은 AI 예측값은 1차 QC 결과가 아니다.

==================================================
7. 지연자료 처리 방식 명확화
==================================================

지연자료는 실제 관측시각과 DB 수신시각을 비교해서 관리한다.

가능하면 상세 데이터에 다음을 표시:
- observation_time
- received_time
- delay_minutes
- delay_flag

지연된 자료가 나중에 수신되더라도:
- 실제 관측값은 실제값으로 표시
- 지연 이력은 보존
- AI 예측값으로 원자료를 대체하지 않는다

그래프에서는:
- 아직 미수신이면 Gap
- 늦게 들어온 자료라면 Late Arrival marker 또는 상태 표시

를 적용한다.

컬럼 예:

==================================================
10. QC 상세검토 화면 신규/개선
==================================================

중요:
AI 예측값, Residual, Drift, 장비이력, RAG 근거는 이 단계에서 보여준다.

상세검토 화면은 “왜 이 값이 이상한가?”에 답해야 한다.

A. 시계열 그래프
- 실제 1분 관측값
- Rule QC Flag 표시
- AI 모델이 실행된 경우에만 AI 정상 기대값(Predicted Value) Overlay
- Residual
- 이상 발생시점 표시

기본 범위:
- 이상 발생 전후 일정시간
예: ±2시간 또는 현재 UX에 맞는 합리적인 범위
사용자가 확대/축소 가능

중요:
AI 결과가 없으면 가짜 예측선을 생성하지 않는다.
“AI 분석 미실행” 또는 “사용 가능한 모델 없음”으로 표시한다.

B. Rule QC 상세
- 어떤 Rule에 걸렸는가
- Threshold
- 실제 값
- Rule Version
- Flag

C. AI 분석
가능한 경우:
- 적용 Model
- Model Version
- Predicted Value
- Residual
- Anomaly Score
- Confidence
- Drift Score
- Level Shift 등 실제 구현된 지표

구현되지 않은 값은 만들어내지 않는다.

D. 장비/센서
- Sensor ID
- Equipment Epoch
- 설치/교체일
- 검교정
- 최근 점검/정비

E. 관련 Evidence
- 운영이력
- 점검보고서
- 유사 과거사례
- 관련 가이드북
- RAG 검색결과

F. 담당자 처리
- 정상 승인
- Suspect
- BAD
- 결측
- 보류
- 반려 등 현재 승인 Workflow에 맞는 Action
- Comment
- Review history

==================================================
11. AI 분석 실행 구조
==================================================

UI 클릭 시마다 처음부터 AI 추론을 실행하는 구조로 만들 필요는 없다.

권장:
- backend에서 신규 관측자료 또는 QC Candidate에 대해 AI 분석을 미리 수행할 수 있으면 pre-compute
- 주요 이상 사례 상세화면에서는 이미 저장된 AI 결과를 조회
- 결과가 없고 사용자에게 실행권한이 있는 경우 “AI 분석 실행” 버튼 제공 가능

하지만 현재 repo에 실제 AI Serving이 완성되지 않았다면:
- fake result 생성 금지
- 미구현 상태를 명확히 표시
- 기존 구현 가능한 API까지만 연결

==================================================
13. Backend/API
==================================================

먼저 현재 QC API를 조사하고 최대한 재사용한다.

필요하다면 다음 기능 수준의 API를 추가한다.
이 이름을 그대로 써야 하는 것은 아니며 현재 프로젝트 Convention을 따른다.

품질 현황 Overview:
GET /api/qc/overview
params:
- date_from
- date_to
- station_id
- variable_code

response에 필요한 내용:
- summary KPI
- flag_distribution
- quality_trend
- rule_qc_counts
- station_variable_matrix
- anomaly_cases
- review_queue

상세:
GET /api/qc/candidates/{id}
또는 기존 Candidate/Review API 확장

response:
- observation
- surrounding_timeseries
- rule_results
- ai_prediction_if_available
- equipment_epoch
- operation_logs
- evidence
- review_history

중요:
대용량 1분 관측자료 전체를 frontend로 전송하지 않는다.
overview는 반드시 backend에서 aggregation한다.

- 집계 Query
- 필요한 index 확인
- pagination
- anomaly list limit
- chart downsampling/aggregation
- loading skeleton
- empty/error state

필요한 경우 SQL Explain 또는 query 구조를 검토하여 병목을 피한다.
